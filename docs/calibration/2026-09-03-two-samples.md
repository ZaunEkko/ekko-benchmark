# 2026-09-03 软件协作协议校准

## 校准目的

本次用两种组织方式不同的真实软件工作区检查 `0.1.0` 评分口径：个人本地多仓协调工作区（样本 A），以及团队共享单仓、使用 OpenSpec 管理变更的工作区（样本 B）。样本只用于发现误报、漏报和画像差异，不是标准答案，也不用于反向调权。样本均为非公开项目，本记录只保留与评分口径有关的结论，不记录项目名称、内部规范编号和文件路径。

扫描器保持只读、离线和确定性，没有执行被测项目的构建、测试、数据库、Git 远程或发布命令。Agent 语义复核同样只读，没有修改两个样本工作区。

## 结果

| 样本 | 画像 | 静态分 | 静态等级 | 静态核心诊断 | Agent 语义分 | Agent 等级 | Agent 核心诊断 |
| --- | --- | ---: | :---: | --- | ---: | :---: | --- |
| 样本 A | `personal-local-multirepo` | 90.5 | A | `limited` | 90.5 | A | `limited` |
| 样本 B | `team-shared-repo` | 74.5 | C | `blocked` | 80.8 | B | `blocked` |

两份结果都只保留一个加权协作分，等级由分数区间直接产生。核心诊断帮助突出主流程风险，但不封顶、不乘系数、不改变分数或等级。样本 A 文档较完整，四项 `partial` 仍通过各自规则权重正常计分。样本 B 的需求、实施和状态同步能力较强，但 Git/远程/发布操作没有人工授权边界，核心诊断因此保持 `blocked`；它不会把 80.8 的 Agent 语义分强行改成 69.9。

## Agent 语义复核差异

样本 A 没有改判。语义阅读确认四个核心 `partial` 都是真实协议缺口，而不是命名或目录结构造成的漏检。

样本 B 有三项改判；其余规则按当前更严格的验收工件口径重新计算：

| 规则 | 静态 | Agent | 依据 |
| --- | --- | --- | --- |
| `decisions.human-confirmed-persistence` | `fail` | `partial` | 研发文档规范的设计模板要求记录“已确认设计约束”，但没有规定由谁确认、未确认时如何提问和保持待确认 |
| `boundaries.documented` | `fail` | `partial` | 工程协作规范定义了单分支目标范围和无关任务隔离，但没有完整说明可写目录、生成物和外部工作区边界 |
| `safety.tracked-local-files` | `fail` | `pass` | 只读检查被跟踪的前端开发环境配置文件后，确认它只有非凭据型配置键；报告不记录配置值 |

这三项把样本 B 从静态 74.5/C 提高到 Agent 语义 80.8/B。语义结果不会覆盖静态基线；`authorization.git-remote-release` 仍为 `fail`，因此核心诊断仍是 `blocked`，但该诊断不再二次改分。

## 规则修正

样本 B 使用 `openspec/changes/README.md` 维护当前变更索引，当前表格明确为空。扫描器最初只识别 `HANDOFF.md` 一类任务级状态文件，错误地把这种空闲状态判成接续失败。本次改为识别任意命名的当前工作索引、常见章节编号以及明确空表；仅有流程说明而没有当前状态记录仍不能通过。

后续多仓校准又补充了以下与样本命名无关的修正：裸 Markdown 文件名和子仓库相对路径可以进入治理文档图；编号式开工流程、先识别目标仓库再读取局部规则、决策替代历史、表格中的明确空闲状态，以及 `typecheck`、`type-check`、`verify:*` 等 npm 检查入口都按等价能力识别。需求触发不会再把 `ACCOUNT_LEVEL_CHANGED` 一类业务标识符误当成英文 `change`，并列出现需求与设计文件也不会自动获得追踪关联分。

根入口在同一条强禁止规则中明确点名不可列举、搜索或读取的相对目录时，扫描器会在遍历前排除并披露未检查范围。“未读取规范不得编码”一类要求读取的规则不会被反向误判成目录禁令。

## 未检查范围

- 未验证样本代码质量、需求实现正确率或真实 Agent 任务成功率；
- 未执行样本的构建、测试、运行时、数据库和外部服务；
- 未验证网络链接、远程仓库状态、发布环境和组织权限；
- 两个样本均扫描了数千个文件和数十个可达治理文档，清单均未截断；
- Windows 本地无法验证 POSIX 权限受限目录场景，该用例由 Linux CI 执行。
