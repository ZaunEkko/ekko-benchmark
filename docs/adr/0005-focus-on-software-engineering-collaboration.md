# ADR-0005：产品只评价软件工程协作

## 状态

已接受。

## 背景

“需求协作”“工作区”和“人机协作”等表述可能让人误以为 Ekko Benchmark 评价小说、视频、研究、设计或通用办公等所有 AI 工作流。当前规则实际检查 Git、工程清单、运行时、代码实施、构建测试、数据副作用和发布授权，适用对象始终是软件项目。

如果将软件工程规则与其他知识工作规则放进同一分数，非软件工作区会因无关规则被扣分或产生大量 `not_applicable`，不同领域的结果也无法公平比较。

## 决策

- Ekko Benchmark 只评价软件工程中的 Coding Agent 协作；
- 目标链路从人的自然语言开发需求开始，到工程上下文恢复、关键澄清、需求与决策沉淀、代码实施、验证和状态同步结束；
- Git、构建、测试、数据库、发布和凭据边界可以参与评分，因为它们属于软件交付过程；
- 不评价内容创作、研究、设计和通用办公等非软件工程工作流，也不规划通用领域能力包；
- 不偏好特定编程语言、框架、Agent 产品或需求工件布局，提供等价软件协作能力的体系应获得等价判断；
- 静态协议分不评价代码质量、模型能力或真实任务成功率，这些结论仍需独立的受控软件任务试验。

## 影响

- README、评分模型、规则目录、贡献指南和安全说明统一使用软件工程边界；
- 后续规则必须能说明它与软件需求理解、代码实施、工程验证或交付安全的关系；
- Java、JavaScript/TypeScript、Python、Go、Rust、.NET、Godot 等工作区都可作为校准样本，但非软件项目不进入同一评分体系；
- 现有 `staticReadiness`、`workflowEffect`、CLI 命令和 JSON Schema 字段保持不变。
