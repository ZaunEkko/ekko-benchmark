# ADR-0006：加权分受核心软件交付门槛约束

## 状态

已被 ADR-0008 取代。维度权重调整仍有效，分数封顶决策不再有效。

## 背景

单纯加权平均会让多个辅助通过项抵消一条关键失败。例如需求工件没有创建触发、Agent 不会主动澄清，或实现后没有验证记录闭环时，入口链接、文件体积和工程清单仍可能把总分推到 A。这种结果数学上正确，却不符合“自然语言软件需求能否沿协议走到安全代码交付”的产品含义。

原画像还把个人多仓的安全权重设为 3，无法表达凭据、删除、数据库和生产副作用在任何软件工作区中的重要性。

## 决策

- 保留九维加权平均并命名为 `weightedScore`，用于解释整体协议覆盖；
- 增加 17 条核心软件交付规则，覆盖启动、澄清、上下文、需求、计划、确认决策、验证、接续、边界和安全；
- 核心规则全部 `pass` 才允许 A；存在非失败缺口时最终分最高 89.9，任一失败时最高 69.9；
- `score` 表示应用门槛后的最终分，等级和 `--min-score` 使用该值；
- 个人与团队画像都将验证设为 18、安全设为 10；两者只在跨仓上下文、状态接续和共享仓库边界上分配不同权重；
- 静态和 Agent 语义评分必须使用同一门槛，并同时报告原始分、最终分和触发规则。

## 影响

- 高分更难通过堆叠辅助文档获得，A 明确表示核心软件交付协议没有已知缺口；
- `partial`、`unknown` 和 waiver 仍保留原有语义，但不能让未证实的核心能力进入 A 或 S；
- 报告和静态 JSON 增加 `weightedScore` 与 `gate`；项目尚未发布，因此将它们纳入首个公开 `1.0` 报告契约；
- 校准目标仍是检查不同软件协作体系的等价能力，不以压低或抬高任何校准样本为目标。
