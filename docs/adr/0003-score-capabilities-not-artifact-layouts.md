# ADR-0003：评分软件协作能力而非工件布局

## 状态

已接受。

## 背景

早期规则使用某个校准样本工作区的 `Spec/Design/ADR/HANDOFF` 组织方式描述需求生命周期。它便于解释，但如果这些名称进入通过条件，就会把一个校准样本错误地变成标准答案，并低估 OpenSpec 或其他软件团队自定义体系提供的等价能力。

## 决策

- 规则以支持代码交付的长期工程约束、软件需求事实、实施计划、人工确认决策、任务状态和验证记录等能力为评价对象；
- 文件名、目录名和具体框架只作为语义识别线索，不能单独构成通过条件；
- 同名文件、同一任务目录、显式引用和外部 ID 都可以建立需求与计划的可追踪关系；
- 任何校准工作区都不是标准答案，不以提高某个样本的分数为目标；
- 核心回归测试至少覆盖 `Spec/Design/ADR/HANDOFF` 风格、OpenSpec 风格和无约定命名的软件协作风格，并保留“只有熟悉名称但没有协议”的反例。

## 影响

- 等价能力在不同工件体系下应得到相同的规则状态；
- 报告建议使用能力语言，不要求用户迁移到特定目录模板；
- 新增识别器时必须用结构不同的正例和命名相似的反例共同验证。
