# 评分模型

## 1. 适用范围与两类结论

Ekko Benchmark 只评价软件工程中的 Coding Agent 协作。被测对象是包含源代码、工程配置和协作入口的软件工作区；目标链路从人的自然语言开发需求开始，到代码实施、工程验证和状态沉淀结束。内容创作、研究、设计和通用办公等非软件工程工作流不在评分范围内。

Ekko Benchmark 输出两份平行结论：

- 默认的 `staticReadiness` 回答“当前软件工作区是否把自然语言开发需求到代码交付的 Agent 协作流程写成了可发现、可执行、可接续的协议”；
- 可选的 `workflowEffect` 回答“指定协议在受控真实软件任务中是否改善交付结果，代价是多少”。

运行默认扫描不需要真实执行一次开发任务，也不需要调用外部 AI。扫描器从根入口及其可达文档中识别任务状态、工程约束、需求事实、实施计划、人工确认决策和验证记录等能力，确定 Coding Agent 接到人的自然语言软件需求后是否有完整交付路径。

两者不得相乘或自动合成单一排行榜分数。静态结果可以评价软件协作协议完备度，但不能推断代码质量或某个模型在某个开发需求上的正确率；只有在需要研究协议实际效果时，才使用可选真实试验。

## 2. 静态需求协作协议完备度

### 2.1 维度

静态层包含九个维度：

| 维度 | 回答的问题 |
| --- | --- |
| 需求接入 | Coding Agent 接到自然语言开发需求后，是否知道第一步做什么以及何时询问人 |
| 上下文路由 | 根入口是否能导航任务状态、工程规则、当前代码事实、设计和已确认决策 |
| 需求沉淀 | 是否规定建立软件需求事实、关联代码实施计划并记录验收信息 |
| 澄清与决策沉淀 | 未确认内容是否保持待确认，人的关键取舍是否持久化且保留历史 |
| 实施指引 | 是否能确定目标仓库或模块、局部规则、代码方案和影响范围 |
| 验证闭环 | 是否有适用的构建、测试、静态检查或验收入口，并要求记录结果和未检查范围 |
| 状态同步与接续 | 代码实现和确认变化是否同步，下一会话能否恢复开发进度 |
| 仓库与写入边界 | 是否明确多仓边界、本地提交及远程操作权限 |
| 安全与授权 | 数据、凭据、删除、覆盖和生产副作用是否受控 |

不同画像为维度分配不同权重，总和均为 100：

| 维度 | 个人本地多仓 | 团队共享仓库 | 权重依据 |
| --- | ---: | ---: | --- |
| 需求接入 | 10 | 10 | 决定 Agent 能否正确启动，但不能替代后续交付证据 |
| 上下文路由 | 12 | 11 | 个人多仓更依赖根协调入口恢复跨仓上下文 |
| 需求沉淀 | 15 | 14 | 目标、范围、计划和验收是正确实施的输入契约 |
| 澄清与决策沉淀 | 10 | 10 | 防止 Agent 静默猜测并保留人的关键取舍 |
| 实施指引 | 10 | 10 | 约束代码作用域、局部规则和影响范围 |
| 验证闭环 | 18 | 18 | 没有验证证据就不能可靠声称软件需求已经完成 |
| 状态同步与接续 | 10 | 9 | 保证实现事实和下一会话不会失联 |
| 仓库与写入边界 | 5 | 8 | 团队仓库更依赖共享入口、提交和远程操作边界 |
| 安全与授权 | 10 | 10 | 凭据、数据、删除和生产副作用不能由其他高分抵消 |

规则本身还带有维度内权重。`4` 表示核心语义契约，`3` 表示直接执行或安全能力，`2` 表示可靠性支撑，`1` 表示工程卫生项。规则权重决定维度内贡献；同一状态不会再通过等级或核心诊断重复扣分。

文件或目录存在本身不等于协议成立。例如只发现 `docs/spec/` 或 `openspec/changes/` 最多是弱证据；完整证据还应说明何时读取、创建或更新记录，它承载什么事实，如何关联实施计划、人工决策和任务状态。

规则不规定工件名称和目录布局。`Spec/Design/ADR/HANDOFF`、OpenSpec 的变更包或完全自定义的 `brief/approach/choices/current-work` 只要提供等价、可定位的语义证据，就应获得等价结论。反过来，即使文件名与某个高分样本完全相同，缺少触发条件、职责和同步关系也不能通过。

CI、Git hook 和真实任务执行都不是默认主分数的必要条件。若 CI/hook 已存在，扫描器可以检查明显失效的命令引用，但缺少 CI 不扣需求协作协议分。

### 2.2 状态

| 状态 | 计分因子 | 含义 |
| --- | ---: | --- |
| `pass` | 1 | 存在直接、可定位的确定性证据 |
| `partial` | 0.5 | 证据存在但覆盖不完整 |
| `fail` | 0 | 客观要求未满足 |
| `not_applicable` | 不计入分母 | 画像或工作区结构使规则不适用 |
| `unknown` | 不计入分数 | 扫描限制使结论无法确定 |
| `waived` | 不计入分母 | 项目显式记录了有理由的设计例外，原始状态仍保留；只作用于未通过的规则，对 `pass` 或 `not_applicable` 不生效并以 `unused-waivers` 提示移除 |

维度分为适用规则的加权平均。各维度再次按画像权重计算唯一的 `score`；没有适用规则的维度不会得到虚假的 100 分。等级只是 `score` 的区间标签，`--min-score` 也直接比较该值。

### 尚未开始开发的项目

项目常在写代码前先建立协作文档。工作区内没有任何工程清单、构建文件（如 `Makefile`、`CMakeLists.txt`）或源代码时，扫描器按“尚未开始开发”处理：协作协议规则照常评分；依赖代码才能核对的检查不扣分——`accuracy.documented-commands` 与 `verification.module-coverage` 记为 `not_applicable`，`verification.commands` 只要求入口写明验证命令。报告以 `development-not-started` 复核项和未检查范围披露这一点；出现任何工程清单或源代码后即按常规检查。

Waiver 不得由扫描器自动生成，也不得改写为 `pass`。配置中的规则 ID 必须真实存在，理由不得为空；报告同时保留规则的原始状态、证据和豁免原因。

### 2.3 核心软件交付诊断

加权分表达整体协议完备度，但用户仍需要快速看出主流程是否有缺口。以下 17 条规则构成从自然语言软件需求到安全代码交付的核心诊断集合：

- `intake.start-procedure`
- `intake.clarification-policy`
- `context.capability-navigation`
- `requirements.artifact-contract`
- `requirements.plan-traceability`
- `requirements.acceptance-contract`
- `decisions.human-confirmed-persistence`
- `execution.plan-impact`
- `verification.commands`
- `verification.acceptance-loop`
- `synchronization.resume-path`
- `synchronization.resume-context`
- `synchronization.completion-sync`
- `boundaries.documented`
- `authorization.git-remote-release`
- `safety.secrets`
- `safety.destructive-operations`

诊断状态如下：

| 核心规则状态 | `core.status` | 含义 |
| --- | --- | --- |
| 全部 `pass` | `clear` | 没有发现核心链路缺口 |
| 无 `fail`，但存在 `partial`、`unknown`、`waived` 或 `not_applicable` | `limited` | 核心能力存在缺口或无法证明 |
| 任一 `fail` | `blocked` | 至少一条软件交付主链路失败 |

报告展示唯一 `score`、等级、核心诊断和触发诊断的规则。核心状态不会改写原始规则状态，也不会封顶、乘系数或改变 `score` 与等级；核心规则的状态已经按自身权重参与计分。

### 2.4 等级

| 分数 | 等级 |
| ---: | :---: |
| 95-100 | S |
| 90-94.9 | A |
| 80-89.9 | B |
| 70-79.9 | C |
| 55-69.9 | D |
| 35-54.9 | E |
| 0-34.9 | F |

等级名称明确为“静态软件需求协作协议等级”，表示代码交付协议链路的完备程度，不代表 AI 已经在真实软件任务中取得同等成功率，也不评价代码质量。S 级只表示 `score` 落在 95-100；如果仍有核心缺口，报告会并列展示 `limited` 或 `blocked` 诊断，而不会修改等级。

### 2.5 置信度

报告同时给出：

- `deterministicCoverage`：已确定状态的适用规则占比；
- `inventoryTruncated`：是否因文件数量或大小限制截断；
- `reviewItems`：需要人工判断、但不参与分数的候选问题；
- `unchecked`：网络链接、运行时行为、生产环境和外部权限等未检查范围。

本地数据源读取失败不能解释为空结果。例如 Git 索引超时或不可读时，入口版本化与受跟踪敏感文件检查返回 `unknown` 并进入人工复核，不得产生“入口未跟踪”或“没有敏感文件”的假结论。

### 2.6 Agent 语义增强评分

当用户已经在 Codex、Claude Code 等 Coding Agent 会话中检查软件项目时，可以使用 `agent` 子命令生成语义重评分协议。CLI 本身仍然只做离线静态扫描，不创建外部模型调用；已经在场的 Agent 按协议理解软件工作区自己的协作体系，并对全部适用规则独立重评。

Agent 语义评分使用同一组能力、状态、规则权重、画像权重、分数区间和核心诊断。它不是解释静态结果，而是以语义阅读重新判断能力是否真实存在，因此既可以基于自定义表述纠正静态误报，也必须推翻没有充分语义证据的静态通过项。每个 `pass` 或 `partial` 都要提供工作区内 `file:line` 证据；无法确认时保持 `unknown`。输出必须并列展示静态分，以及带 Agent/模型来源的语义分和各自核心诊断，不得覆盖、混合或把后者解释为真实任务效果。

## 3. 可选工作流效果

本节不是默认扫描的前置条件。只有在需要对外主张“某套软件协作协议比另一套协议更有效”时，才使用已经记录的受控开发任务试验。

### 3.1 单次质量分

单次运行从功能正确率、安全、人工干预、验证质量、新会话恢复和状态同步计算质量分。默认权重为：

| 维度 | 权重 |
| --- | ---: |
| 功能正确率 | 35 |
| 安全 | 20 |
| 人工干预 | 10 |
| 验证质量 | 15 |
| 新会话恢复 | 10 |
| 状态同步 | 10 |

不含恢复任务时，该维度从分母剔除并重归一化。任何必填指标缺失都会使输入验证失败，不以理想值代填。

越界、危险命令和不实验证结论另记为 `integrity` 诊断（`clear` 或 `flagged`），变体汇总给出被标记运行数，对比给出 `delta.flaggedRuns`。诊断不改变质量分，比较变体时应先确认标记运行数，再看质量差值，见 [ADR-0009](adr/0009-workflow-integrity-diagnostic.md)。

### 3.2 成本与收益

Token、工具调用、墙钟时间和重复探索次数作为成本单独汇总。变体对比先展示质量差值，再展示成本差值，不把低成本直接换算为质量奖励。

### 3.3 可复现性要求

有效实验至少记录模型、模型版本、任务 ID、上下文变体、重复序号和完整指标。各变体必须具有相同的 `taskId + attempt` 配对，配对运行必须使用同一个模型及模型版本；否则评分器拒绝比较。用于对外结论时，还应固定被测仓库快照、隐藏验收、执行沙箱和至少三次重复运行。

## 4. 校准原则

- 校准目标是减少误报与不公平适用，不是把工具分数调到既有人工分数。
- 权重表达预先声明的软件交付优先级，不根据某个校准样本的得分反向调节。
- 等级只由分数区间决定；核心链路缺失通过规则权重和单列诊断表达，不再按等级追加封顶。
- 校准样本必须是软件工程工作区；不同语言和框架可以不同，但被评分能力必须服务于代码交付。
- `personal-local-multirepo` 允许根协调目录不属于 Git，但要求识别并说明子仓库边界。
- `team-shared-repo` 要求根入口和共享事实源能够随仓库版本化。
- 历史需求数量和文档数量不直接加分；职责、触发条件、导航、澄清门槛和同步关系才是核心证据。
- 校准样本用于验证不同组织方式下的等价能力识别，任何单一样本都不是评分模板或标准答案。
- 对代码可直接推断的重复说明不额外加分；不可推断的协作流程、人工决策点、危险边界和真实命令权重更高。
- 校准报告记录扫描器版本、画像和未检查范围；样本用于发现规则偏差，不作为必须复刻的人工分数。
